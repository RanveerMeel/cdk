# CDK v0.1.0 — preview release

**CDK (Cognitive Distributed Kernel)** is an open-source, bare-metal Rust
kernel for running AI agents under kernel-enforced, cryptographically
provable permissions, built on post-quantum cryptography from the start.

> **Preview — not for production use.** v0.1.0 is for evaluation, research
> and review. Interfaces will change. It has had automated reviews and
> extensive testing, but no independent security audit yet
> ([SECURITY-REVIEW.md](../../SECURITY-REVIEW.md)).

## What is in this release

**Trust core**
- Hybrid **Ed25519 + ML-DSA-65** (FIPS 204) capability tokens issued and
  verified by the kernel; no ambient authority.
- Tamper-evident, hash-chained **audit log** with hybrid-signed checkpoints.
- Key hygiene: zeroized keys, scrubbed crypto stack, zero-on-free heap.
- Crypto tested against **NIST ACVP** vectors (ML-DSA-65, ML-KEM-768,
  Ed25519, SHA-256 — 854 cases) and RFC vectors (HKDF, X25519,
  ChaCha20-Poly1305). This is testing, not CAVP or FIPS 140 validation.

**Agent runtime**
- Agents are isolated ring-3 Rust programs loaded from a signed ramdisk,
  holding capability handles that can only be weakened, never strengthened.
- Preemptive scheduling with a CPU-budget watchdog; fault containment.
- Native integer-only ML inference inside agents.

**Human oversight**
- Approval-gated capabilities; with operator keys pinned, approvals are
  **post-quantum signatures from named operators** — M-of-N quorums,
  vetoes, time-outs — verified by the kernel.
- **Policy change review**: every grant or gateway change is shown as a
  reach diff and checked against invariant rules
  (`deny`, `separate`, `approval`, `quorum`) before it applies.

**Connected agents**
- Post-quantum secure link to a Linux host gateway (X25519 + ML-KEM-768,
  hybrid-signed, pinned gateway identity).
- Tools through **MCP** and models on Linux (vLLM, llama.cpp, Ollama, any
  OpenAI-compatible server) — API keys stay in the gateway, never reach
  agents.

**Boot integrity**
- **Verified boot**: the ramdisk (programs, keys, policy) must match a
  manifest signed by the release key compiled into the kernel, or the
  kernel locks down.
- **Measured boot**: firmware → CDK's measuring UEFI loader → kernel, in TPM
  PCRs; **TPM quotes** let the gateway refuse any machine, firmware, loader,
  kernel or ramdisk other than the expected ones.

**Assurance**
- Ten libFuzzer targets over every parser of untrusted bytes (CI), an
  in-kernel syscall fuzzer, AddressSanitizer on host tests.
- An end-to-end **fraud-prevention demo** (`tools/demo_fraud.sh --auto`,
  synthetic data): two agents, two-person approvals, a prompt-injected
  transaction that cannot move money ([DEMO.md](../../DEMO.md)).

## Artifacts

| File | What it is |
|---|---|
| `cdk-0.1.0-src.tar.gz` | The complete source (`git archive` of the tagged commit) |
| `cdk-kernel-x86_64.elf` | The kernel, with the CDK release public key compiled in |
| `cdk-uefi-loader.efi` | CDK's measuring UEFI loader (fork of rust-osdev `bootloader-x86_64-uefi` 0.11.17) |
| `cdk-ramdisk-eval.tar` | Evaluation ramdisk: agent programs, default policy, signed boot manifest. **No deployment keys** (no gateway identity, no operators) |

| `cdk-0.1.0.cdx.json` | Software bill of materials (CycloneDX 1.5) |
| `cdk-release.pub` | CDK release public key (hybrid Ed25519 + ML-DSA-65) |
| `SHA256SUMS`, `SHA256SUMS.sig` | Checksums of every file, signed with the release key |
| `REPRODUCIBILITY.txt` | Result of building the release twice from source |

## Verify the release

```bash
sha256sum -c SHA256SUMS
# With CDK built from the source archive (tools/sign.sh builds cdk-sign):
tools/sign.sh verify-file /path/to/SHA256SUMS --pub /path/to/cdk-release.pub
```

The signature binds the file name and contents under the FIPS 204 context
`CDK-RELEASE-v1`; both the Ed25519 and the ML-DSA-65 halves must verify.

**Reproduce it**: `tools/release.sh 0.1.0` builds the source twice in
different directories, offline, and refuses to sign unless every artifact is
byte-identical. With the same toolchain (pinned in `rust-toolchain.toml`) and
crate versions (`Cargo.lock`), your build must produce the same SHA-256 —
except for the release key: the kernel embeds it, so a build with your own
key produces your own (equally reproducible) artifacts.

## Try it

```bash
# UEFI with a TPM (QEMU + OVMF + swtpm): measured boot end to end
./run_qemu.sh                     # from the source tree; builds everything
# or boot the evaluation image directly (BIOS):
qemu-system-x86_64 -cpu max -drive format=raw,file=cdk-0.1.0-eval.img -serial stdio -display none
```

At the `cdk>` prompt: `boot`, `issuer`, `capverify obj-1`, `spawn hello`,
`elf-run 1`, `policy`, `audit-verify`. For the gateway, tools, models and
signed approvals, build from source: deployments generate their own gateway
identity, operator keys and release key (README.md).

## Known limitations

- Preview quality; no independent security audit yet.
- Agents run on one CPU (roadmap 2.7); no FPU/SIMD state for agents (2.6).
- UEFI Secure Boot is not enabled (the loader is measured, not verified, by
  firmware); TPM enrollment is trust-on-first-use (no endorsement
  certificate check); under BIOS the kernel measures itself.
- Operator keys are files (hardware tokens are future work).
- x86_64 only (ARM64 is roadmap 4.1).
