# CDK v0.3.0 — preview release

**CDK (Cognitive Distributed Kernel)** is an open-source, bare-metal Rust
kernel for running AI agents under kernel-enforced, cryptographically
provable permissions, built on post-quantum cryptography from the start.

> **Preview — not for production use.** v0.3.0 is for evaluation, research
> and review. Interfaces will change. It has had automated security reviews
> and extensive testing, but no independent security audit yet
> ([SECURITY-REVIEW.md](../../SECURITY-REVIEW.md)).

## What is new since v0.2.0

**Runs on modern machines: x2APIC fix.** v0.2.0 crashed while starting its
other CPUs wherever the processor offers x2APIC — QEMU 10, KVM, and
essentially every modern server and cloud VM: it switched the boot CPU to
x2APIC but kept using the older xAPIC registers elsewhere. Every CPU now
uses the boot CPU's mode. CDK now also runs under **KVM**.

**A memory that survives reboots: the sealed store** (roadmap 4.5)
- Revocations, and the record of which peer messages and capabilities a
  node already accepted, persist across reboots: a revoked delegation stays
  revoked, a delivered message cannot be replayed.
- The gateway keeps the store but can neither read, change nor roll it
  back: the records are encrypted under a key the TPM releases only to the
  measured boot chain (firmware, loader, and the kernel as the loader
  measured it), and a TPM monotonic counter catches an old copy.
- A missing, rolled-back, tampered or foreign store **fails closed**: peers'
  messages and imports are refused until the operator's reviewed
  `store-reset`. `require sealed-store` in the default policy refuses them
  whenever the store is not open (TPM removed, BIOS boot).
- **Updates keep it:** before a kernel, loader or firmware update,
  `store-migrate <pcr>=<hex>…` — with the updated chain's PCR values — re-seals
  the store so the updated boot chain opens it too, and the current one still
  can (TPM `PolicyOR`; no classical signing key in the trust chain). Once
  updated, `store-migrate` without values drops the old chain's access.

**Deployment: first steps** (roadmap Phase 5, [docs/DEPLOYMENT.md](../DEPLOYMENT.md))
- **Docker** (5.1): `cdk:<version>` boots a signed release at the `cdk>`
  prompt; `cdk:dev` runs the whole stack from source in one container.
- **vsock link** (5.2): the kernel–gateway link also runs over virtio-vsock,
  the transport of KubeVirt, Firecracker and QEMU's `vhost-vsock-pci` —
  the prerequisite for running CDK as a micro-VM with its gateway beside it.

**Reproducible builds, for real:** the toolchain is now pinned
(`nightly-2026-08-05` in `rust-toolchain.toml`) and used by every script.
v0.2.0's notes said it was pinned, but the file named only `nightly`.

## Upgrading from v0.2.0

- On each TPM machine, run `store-reset` once after the first
  `link-secure` to create the sealed store (a reviewed decision; until then
  peers' messages and imports are refused).
- Before later kernel, loader or firmware updates, run
  `store-migrate <pcr>=<hex>…` with the new boot chain's PCR values (PCR 11
  is the new build's `loader 11` line in `boot.measurements`; see
  ARCHITECTURE.md, Sealed Store). **`store-migrate` without values re-seals
  to the current chain only** — run it after the update, from the new
  kernel, when the old one must lose access; run before the update, it
  would leave the new kernel unable to open the store.
- Install the pinned toolchain: `rustup toolchain install` in the
  repository.
- Switching QEMU between emulation and KVM changes the firmware's CPU
  measurement: TPM machines must enroll again (`CDK_QEMU_ACCEL=kvm` opts in;
  emulation stays the default).

## Verify the release

```bash
sha256sum -c SHA256SUMS
# With CDK built from the source archive (tools/sign.sh builds cdk-sign):
tools/sign.sh verify-file /path/to/SHA256SUMS --pub /path/to/cdk-release.pub
```

The signature binds the file name and contents under the FIPS 204 context
`CDK-RELEASE-v1`; both the Ed25519 and the ML-DSA-65 halves must verify.
The release key ID is `0b57f6795dcdf315f2512079b8e16ba8` (unchanged since
v0.1.0). `verify-file` prints it, and the evaluation image prints its first
eight hex digits at boot (`Boot: VERIFIED ... release key 0b57f679`). Check
it against this page on GitHub, not only against the downloaded
`cdk-release.pub`.

**Reproduce it**: `tools/release.sh 0.3.0` builds the source twice in
different directories, offline, and refuses to sign unless every artifact is
byte-identical. With the toolchain pinned in `rust-toolchain.toml` and the
crate versions in `Cargo.lock`, your build must produce the same SHA-256 —
except for the release key: the kernel embeds it, so a build with your own
key produces your own (equally reproducible) artifacts.

## Try it

```bash
# The evaluation image directly (4 CPUs):
qemu-system-x86_64 -cpu max -smp 4 -drive format=raw,file=cdk-0.3.0-eval.img -serial stdio -display none
# In Docker, the release (signature checked at build) or the whole stack from source:
docker build -f docker/Dockerfile --target eval -t cdk:0.3.0 .
docker run -it --rm cdk:0.3.0
docker build -f docker/Dockerfile --target dev -t cdk:dev .
docker run -it --rm --init -v cdk-target:/cdk/target cdk:dev
```

On Linux hosts with KVM, add `-accel kvm` to QEMU or `--device /dev/kvm` to
`docker run` for much faster runs (optional; see docker/README.md).

At the `cdk>` prompt: `boot`, `spawn hello`, `run-all`, `policy`,
`audit-verify`; with the gateway (`cdk:dev`): `link-secure`, `store-reset`,
`tools-sync`, `store`.

## Known limitations

- Preview quality; no independent security audit yet.
- Tested on QEMU's virtual hardware (emulation and KVM) only. The TPM driver
  speaks the TIS interface; cloud vTPMs and firmware TPMs use CRB (roadmap
  5.3). Docker's default security profiles forbid vsock inside containers:
  with `CDK_LINK=vsock`, run the gateway on the host.
- Sealed store: the key crosses the TPM bus unencrypted when unsealed;
  anyone with the TPM owner hierarchy (usually no password) can increment or
  delete the counter — a detected, fail-closed denial of service.
- Distributed capabilities: delivery is pulled by the operator
  (`peer-sync`); only `send` is forwarded; node authorities expire but
  cannot yet be revoked early; time comes from the gateway's clock.
- TPM endorsement supports ECC P-256 endorsement keys with the certificate
  in TPM NV; Secure Boot is opt-in and its signatures are RSA (a UEFI
  constraint); operator keys are files.
- x86_64 only (ARM64 is roadmap 4.1).
