# CDK v0.2.0 — preview release

**CDK (Cognitive Distributed Kernel)** is an open-source, bare-metal Rust
kernel for running AI agents under kernel-enforced, cryptographically
provable permissions, built on post-quantum cryptography from the start.

> **Preview — not for production use.** v0.2.0 is for evaluation, research
> and review. Interfaces will change. It has had automated security reviews
> and extensive testing, but no independent security audit yet
> ([SECURITY-REVIEW.md](../../SECURITY-REVIEW.md)).

## What is new since v0.1.0

**Distributed capabilities** (roadmap 3.5)
- CDK nodes delegate to each other. The registry root authorizes each
  gateway for **one node name**; that gateway certifies its node's per-boot
  key only after accepting the node's attestation, and every node pins the
  root in its signed ramdisk.
- `cap-export` turns an agent's handle into a **portable capability** for
  one named peer node, after a delegation review and operator confirmation
  (or signed approvals). `cap-import` on the peer checks the certificate
  chain, signature, audience, expiry and replay, then its own
  `trust <node> <object> <perms>` policy, and grants a handle on the proxy
  `peer:<node>/<object>` through the normal policy review.
- `peer-sync` carries agents' messages to the owning node, which verifies
  sender, its own delegation, signatures, permission, replay and
  revocation before delivering. `cap-revoke` withdraws a delegation.

**Agent runtime**
- **Agents on every CPU** (2.7): per-CPU scheduling with work stealing;
  `run_qemu.sh` starts 4 vCPUs.
- **Per-agent FPU/SSE/AVX state** (2.6): agents can use hardware floating
  point and vector registers, saved and restored per agent with XSAVE; CI
  checks the kernel itself never touches them.

**Boot integrity** (roadmap 4.2, now complete)
- **TPM endorsement**: with `--tpm-ca`, the TPM must prove it is genuine —
  its endorsement-key certificate chains to a manufacturer CA, and
  `MakeCredential`/`ActivateCredential` proves the quoting key is in that
  TPM. Enrollment is no longer trust-on-first-use.
- **UEFI Secure Boot** (`CDK_SECURE_BOOT=1`): firmware runs only a loader
  signed with the deployment's key, and that loader runs only the kernel
  whose SHA-256 is built into it.

**Security reviews** (SECURITY-REVIEW.md §4)
- Endorsement: one proof per challenge in constant time; EK certificates
  must carry the TCG EK usage.
- Distributed capabilities: gateways no longer hold the registry root key
  (a compromised gateway can speak only for its own node); exact object
  names on delivery; reviewed exports.
- Signed approvals are denied, never shown cut short, when their
  description does not fit one request; the RNG reports an insecure source
  once its fallback has been used.

## Upgrading from v0.1.0

- Re-enroll TPM machines once: the UEFI loader and the CPU count are
  measured (delete `target/tpm-enrollment*`).
- User programs now build for `user/x86_64-cdk-user.json`
  (`tools/build_user_programs.sh`).
- Distributed capabilities need a node authority per gateway:
  `tools/sign.sh node-authority <node> --root target/registry.key`
  (`run_gateway.sh` creates it in development).

## Verify the release

```bash
sha256sum -c SHA256SUMS
# With CDK built from the source archive (tools/sign.sh builds cdk-sign):
tools/sign.sh verify-file /path/to/SHA256SUMS --pub /path/to/cdk-release.pub
```

The signature binds the file name and contents under the FIPS 204 context
`CDK-RELEASE-v1`; both the Ed25519 and the ML-DSA-65 halves must verify.
The release key ID is `0b57f6795dcdf315f2512079b8e16ba8` (unchanged since
v0.1.0). `verify-file` prints it, and the evaluation image prints its first
eight hex digits at boot (`Boot: VERIFIED ... release key 0b57f679`). Check
it against this page on GitHub, not only against the downloaded
`cdk-release.pub`.

**Reproduce it**: `tools/release.sh 0.2.0` builds the source twice in
different directories, offline, and refuses to sign unless every artifact is
byte-identical. With the same toolchain (pinned in `rust-toolchain.toml`) and
crate versions (`Cargo.lock`), your build must produce the same SHA-256 —
except for the release key: the kernel embeds it, so a build with your own
key produces your own (equally reproducible) artifacts.

## Try it

```bash
# UEFI with a TPM (QEMU + OVMF + swtpm): measured boot end to end
./run_qemu.sh                     # from the source tree; builds everything
# or boot the evaluation image directly (BIOS, 4 CPUs):
qemu-system-x86_64 -cpu max -smp 4 -drive format=raw,file=cdk-0.2.0-eval.img -serial stdio -display none
```

At the `cdk>` prompt: `boot`, `issuer`, `capverify obj-1`, `spawn hello`,
`elf-run 1`, `run-all`, `policy`, `audit-verify`. For the gateway, tools,
models, signed approvals and distributed capabilities, build from source:
deployments generate their own gateway identity, operator keys, registry
root and release key (README.md).

## Known limitations

- Preview quality; no independent security audit yet.
- Distributed capabilities: delivery is pulled by the operator
  (`peer-sync`); only `send` is forwarded; replay protection is per boot of
  the receiving node; revocations survive the issuing node's reboots only
  through its gateway's file (no persistent sealed storage yet); node
  authorities expire but cannot yet be revoked early; time comes from the
  gateway's clock.
- TPM endorsement supports ECC P-256 endorsement keys with the certificate
  in TPM NV (discrete TPMs); firmware TPMs and RSA-only EKs are not yet
  supported, and EK certificate revocation is not checked.
- Secure Boot is opt-in; its signatures are RSA (a UEFI constraint).
- Operator keys are files (hardware tokens are future work).
- x86_64 only (ARM64 is roadmap 4.1).
