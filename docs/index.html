CDK — the quantum-safe agent trust kernel

AI agents are starting to act: move money, read case files, call tools. CDK is a bare-metal Rust kernel where an agent can only do what the kernel has cryptographically allowed it to do. Its permissions are signed with hybrid classical and post-quantum cryptography, and the kernel checks them on every action.

Why a trust kernel for agents

Most agent platforms enforce permissions in user space, on top of a general-purpose OS. Anything that compromises the layer underneath can bypass them. CDK puts the rules in the kernel itself.

Agents are isolated processes

Each agent runs in ring 3 with its own address space. User memory lives in a dedicated page-table slot, and every pointer a syscall touches is checked before it's read.

Capabilities, not ambient authority

No root user. An agent can only reach an object, tool, model, or network endpoint if it holds a capability the kernel issued for it.

Quantum-safe by default

Capability tokens carry hybrid Ed25519 + ML-DSA-65 (NIST FIPS 204) signatures. Both must verify, so forging one means breaking both schemes.

How a capability is checked

  1. Kernel issuer at boot The kernel generates an Ed25519 key pair and an ML-DSA-65 key pair from the CPU's hardware RNG and pins their fingerprint.
  2. Signed tokens Each token's object, permissions, format, and algorithm ID are hashed with domain separation and signed with both keys, so a token can't be downgraded to a weaker algorithm.
  3. Verified against the pinned issuer Unsigned, self-signed, tampered, or escalated tokens are rejected on every privileged operation. 
cdk> capverify obj-1
  unsigned                     rejected (no valid proof)
  forged (attacker issuer)     rejected (UnknownIssuer)
  kernel-issued                accepted
  kernel-issued + escalated    rejected (no valid proof)

Where CDK fits

CDK isn't a GPU driver project or a Linux replacement. Heavy inference runs on Linux with the vendor stack. CDK is the control plane: it decides which agent may use which model or tool, with what data, and records that it happened. 

┌──────────── CDK (trust kernel) ────────────┐     ┌──────── Linux ────────┐
│ agents = isolated ring-3 processes         │     │ GPU driver + CUDA/... │
│ hybrid PQ-signed capability tokens         │     │ inference servers     │

Status

Early development preview, not for production use. What exists today and what's next:

Working now

  • x86_64 bare-metal boot, SMP, preemptive scheduling, serial console
  • Ring-3 processes from ELF, isolated address spaces, clean exit and reap
  • Hybrid Ed25519 + ML-DSA-65 capability tokens, verified against the pinned kernel issuer
  • Dedicated crypto stack for post-quantum operations
  • Capability-gated IPC and networking
  • Tamper-evident audit log: SHA-256 hash chain with hybrid-signed checkpoints
  • Fault containment: a crashing agent is terminated and logged; the kernel keeps running
  • Key hygiene: zeroized keys, scrubbed crypto stack, zero-on-free heap, known-answer tests

Next on the roadmap

  • Per-agent capability handles and human-approval gates
  • Hybrid X25519 + ML-KEM-768 channel to Linux; MCP gateway
  • Native CPU inference demo; ARM64 port

Kernel architecture

Quick start

rustup target add x86_64-unknown-none
rustup toolchain install nightly
rustup component add rust-src llvm-tools-preview --toolchain nightly
sudo apt install qemu-system-x86

./run_qemu.sh

At the cdk> prompt try issuer, capverify obj-1, and elf-smoke, or type help.

Open core

Open source (Apache-2.0)

The kernel, capability model, agent runtime, and all cryptography. Algorithms and formats are always public; security rests on keys, not on secrecy.

Editions for regulated sectors

For finance and defense: quantum key distribution (QKD) integration (always combined with ML-KEM), hardware security modules (HSMs), certified builds, sector policy packs, and support.

CDK is intended for defensive and protective computing with human oversight of consequential actions.
